# 关键决策记录（ADR）

> 这份文档记录**为什么这么设计**，以及当时考虑过什么别的方案。
>
> 需求文档写「做成什么样」，ADR 写「为什么不那样做」。后者更容易丢，
> 而它恰恰是新人接手时最想知道的东西 —— 否则他们会把每一个决定重新推翻一遍。

格式：每条 ADR 包含 **背景 → 可选方案 → 决定 → 理由 → 代价与缓解**。

---

## ADR-001 用岗位能力模型做底座，而不是训练一个筛简历的模型

**状态**：已采纳 ｜ **影响**：整个产品架构

### 背景

要让 AI 判断候选人合不合适，有两条路：训一个模型直接输出「合适/不合适」，
或者把判断拆解成结构化的能力项逐项评估。

### 可选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A. 端到端模型 | 实现直接，端到端指标好看 | 不可解释；换岗位要重训；无法追责 |
| B. 能力模型 + 逐项评估 | 可解释、可溯源、换岗位只换配置 | 需要前期投入做能力模型冷启动 |

### 决定

选 B。

### 理由

访谈里的一个数字决定了这件事：**双人复核 40 份，档位不一致 11 份（27.5%）。**
也就是说，HR 之间自己都不一致。这种情况下训一个端到端模型是**把噪声当标签** ——
模型学到的不是「什么样的人合适」，而是「标注入标注时的心情」。

能力模型的作用不是让 AI 更准，而是**先把人的判断标准统一起来**。
统一之后，AI 的不一致才有意义可谈。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 前期要做能力模型冷启动 | 用三路并行方法：正向拆解 + 历史样本反向挖掘 + 专家校订 |
| 新增岗位需配置 | 提供模板派生，派生后能力项与权重完整继承 |

## ADR-002 「未体现」和「不符合」必须分开

**状态**：已采纳 ｜ **影响**：打分逻辑、出题逻辑、复核页

### 背景

简历里没有某项能力的证据，有两种可能：候选人真的不具备，或者只是**没写**。
如果都标成「不符合」，就等于惩罚了简历写得简略的人。

### 可选方案

| 方案 | 后果 |
| --- | --- |
| A. 统一标「不符合」（0 分，计入分母） | 简历简略者系统性低分 |
| B. 统一标「未体现」（不计分，不计分母） | 简历注水者反而占便宜 |
| C. 三态区分：命中 / 部分命中 / 未体现 + 不符合 | 需要额外判断逻辑 |

### 决定

选 C，且「未体现」**不给分、也不计入分母**。

### 理由

这是简历筛选里最常见的**不公平来源**。计入分母会让「没写」等价于「不会」，
而候选人是否写全某项经历，往往与岗位无关（有人习惯详写，有人习惯略写）。

不计入分母则意味着：总分反映的是「已知信息下的匹配度」，而不是「全面考核」。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 简历很空的人可能因分母小而得高分 | 置信度独立计算，分母过小则置信度低 → 落入中间档强制人工复核 |
| 面试官可能把「未体现」误解为「不会」 | 复核页与准备页均显示文案：「简历未提及，需在面试中验证」 |

**这条决策的直接下游**：差集出题（ADR-004）。正因为区分了「未体现」，
才可能针对未体现项出题去验证 —— 两个决策是连在一起的。

## ADR-003 采纳与否决不设默认选中，理由是一句话访谈

**状态**：已采纳 ｜ **影响**：复核页交互

### 背景

候选人在待复核列表里，HR 要逐份处理。为了提速，最自然的做法是预设一个默认按钮。

### 可选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A. 高置信度默认选中「采纳」 | 快 | 无意识批量放行，错误被放大 |
| B. 不设默认 | 每次都要主动选择 | 慢一点 |

### 决定

选 B。**并且中间档禁用批量通过。**

### 理由

访谈里 5 位 HR 有 5 位把「AI 不准还要我背责任」列为首要顾虑，而不是「AI 不准」。
这意味着：**用户要的不是更准，而是「决定权在我、且有据可查」。**

不设默认的作用不是提高准确率，而是让每一次采纳都是一个**主动决定**。
配合决策日志留痕，责任边界就清楚了：AI 给建议，人做决定，日志记录双方。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 操作变慢 | 「采纳与否决一键完成，无需理由即可继续」—— 降低的是摩擦，不是把关 |
| 中间档禁用批量会显著变慢 | 这是**故意的**：这部分恰是模型最没把握的样本，值得多花时间 |

## ADR-004 差集出题，并且必须后置强制约束

**状态**：已采纳 ｜ **影响**：面试出题

### 背景

面试时间有限（通常 30 分钟），出题要覆盖最需要验证的能力项。
最自然的做法是把能力项和简历一起丢给模型，让它出题。

### 决定

出题输入是**差集**（简历未体现 + 部分命中的能力项），
且生成后有**一道代码侧的强制约束**，不信任模型自觉。

### 理由

模型会**优先出简历上已经写得很好的部分** —— 因为那些内容在提示词里最"显著"，
生成起来也最顺。实测中它会违反差集约束，反复出「请介绍你那个订单中心重构」这类
简历上已经写清楚的问题。

所以差集不能只写在提示词里，必须有后置纠正：

| 类别 | 约束 |
| --- | --- |
| 排除条款（如真实性存疑） | 最多 1 道核验题，**不能**出成「你有没有造假」 |
| 普通缺口项 | 优先保留 |
| 已证明项 | 每项最多 1 道确认题 |
| 时间预算 | 30 分钟方案总时长 ≤ 32 分钟 |

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 后置纠正会让部分生成结果被丢弃 | 缺口题不足时用缺口项补满预算，而不是直接少出题 |
| 排除条款仍可能被当普通缺口项 | 代码侧硬约束 + 出题日志可查 |

## ADR-005 版本号以代码侧为准，丢弃模型自报的版本

**状态**：已采纳 ｜ **影响**：所有 AI 产出

### 背景

AI 输出要带元信息（模型版本、提示词版本），方便归因。

### 可选方案

| 方案 | 后果 |
| --- | --- |
| A. 让模型在输出里自报版本 | 模型可能编造不存在的版本号 |
| B. 代码侧写死 | 版本一定真实 |

### 决定

选 B。

### 理由

模型会**编造**。它会输出一个格式正确但内容不存在的版本号，
而这类错误最难发现 —— 因为它看起来完全正常。

一旦版本不可信，线上效果波动就无法归因，离线回归也失去对比基准。
**元信息是给人用来做判断的，不能由被判断的对象自己填。**

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 需要维护代码侧的版本映射 | 提示词版本已集中管理，模型版本从路由配置读取 |

## ADR-006 反作弊分三层，只有第一层是真防线

**状态**：已采纳 ｜ **影响**：考试模块

### 背景

在线考试要防作弊。直觉做法是监听浏览器事件（切屏、粘贴、开发者工具），
发现异常就判失败。

### 决定

拆成三层，并且**明确只有第一层是真实防线**：

| 层 | 内容 | 性质 |
| --- | --- | --- |
| 一 | 服务端强制：答案不下发、开考即冻结试卷、服务端计时、随机组卷 + 选项乱序、限次幂等 | **真实防线，不可绕过** |
| 二 | 客户端信号：切屏、粘贴、失焦、开发者工具、答题速度 | **仅线索，可绕过** |
| 三 | 人工复核：带教人看信号明细，决定是否作废、给终评分 | **最终判断** |

### 理由

浏览器事件**技术上不可能防住有心作弊的人**，而且会大量误伤：

| 无辜场景 | 会触发 |
| --- | --- |
| 接电话切出去 | 切屏、页面隐藏 |
| 输入法弹窗 | 失焦 |
| 笔记本合盖 | 页面隐藏、全程未聚焦 |
| 网课页面同时开着 | 多标签页 |

若据此自动判失败，直接违背洞察二「误杀的代价远高于漏放」。
所以：**服务端让作弊拿不到答案，客户端把可疑的挑出来给人看，人看证据决定。**

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 需要人复核，不能全自动 | 风险分排序，把可疑的排前面，降低复核成本 |
| 作废会消耗新人机会 | 作废时**返还考试机会** |

### 附带的工程陷阱

选项乱序后，判分时**必须把答案反映射回题库原序**。漏掉这一步，
每一道客观题都会判错 —— 而且因为结果是"全错"而非"报错"，
很容易被误认为题目太难。

## ADR-007 不自建视频面试，只做「把正确的人送进正确的会议」

**状态**：已采纳 ｜ **影响**：面试模块

### 背景

面试分视频/现场/电话。视频面试最自然的想法是平台内置音视频。

### 可选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A. 自建 WebRTC | 体验统一、数据闭环 | 要解决 NAT 穿透、弱网、录制存储、合规；工期数倍 |
| B. 接入现有会议工具 | 几乎零成本，用户已熟悉 | 会议数据不在平台内 |

### 决定

选 B。平台**只负责把会议入口、时间与身份安全地送到双方手里。**

### 理由

范围里明确不做「AI 面试官与无人化视频面试」，自建音视频解决的是与本期问题定义
无关的技术问题。而平台真正缺的其实是三件小事：

1. 面试官不知道会议链接在哪 → 准备页顶部直接放入口
2. 候选人没有账号不知道从哪进 → 一次性邀请链接
3. 录音同意没有采集渠道 → 候选人在链接页表态

**做产品最难的是分清「缺功能」和「缺信息」。** 这三条都是后者。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 会议数据无法用于分析 | 评估报告仍由逐字稿驱动，与会议工具无关 |
| 依赖第三方可用性 | 方式分三种，视频不可用时可用电话；会议链接手填即可 |

## ADR-008 候选人用一次性链接，不注册账号

**状态**：已采纳 ｜ **影响**：候选人侧

### 背景

候选人要查看面试时间、进入会议、确认录音意愿，需要某种身份。

### 可选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A. 候选人注册账号 | 可复用、有历史 | 为一场面试注册，流失大；平台个人信息范围扩大 |
| B. 一次性邀请链接 | 零门槛 | 链接本身就是凭据，需要防护 |

### 决定

选 B，并按「这两个接口不要求登录」的标准收紧：

| 约束 | 实现 |
| --- | --- |
| 不可枚举 | 32 字节随机令牌，而非自增 id |
| 不泄露存在性 | 无效/过期/取消统一返回 404 与同一句提示 |
| 最小返回 | 不含面试官姓名、题目、评分、简历、联系方式 |
| 可撤销 | 取消或「重发链接」后旧链接立即失效 |
| 自动过期 | 面试结束 24 小时后失效 |
| 面试官不可代答 | 面试官端接口不返回邀请令牌 |

### 理由

**收集个人信息的第一原则是不收集。** 候选人不是平台用户，
为一个不需要持续关系的场景要求注册，既增加流失，也扩大了需要保护的数据范围。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 链接转发即泄露 | 只含本场信息；发现后一键重发使旧链接失效 |
| 候选人无法查看历史 | 一场面试一个链接，符合实际使用场景 |

## ADR-009 业务线是受控字典，不是自由文本

**状态**：已采纳 ｜ **影响**：账号、岗位、知识库

### 背景

业务线决定用人经理能看到哪些候选人、知识库按什么范围检索。

### 可选方案

| 方案 | 后果 |
| --- | --- |
| A. 自由文本输入 | 账号填「电商业务线」、岗位填「电商线」，字符串不相等 |
| B. 受控字典 | 需要管理界面，但不会不一致 |

### 决定

选 B，且账号、岗位、知识库**只能从字典选择**，后端同样校验。

### 理由

隔离失效最危险的形态**不是报错，而是静默地少看到数据**。
A 方案下，一位用人经理可能一个候选人都看不到，而系统不会给出任何提示 ——
他会以为「还没有候选人」，而不是「数据被过滤掉了」。

这个缺陷在本项目里真实发生过两次：
一次是业务线自由文本，一次是隔离条件写成了判断「部门」而过滤用「业务线」，
导致没填部门的经理能看到**全部**候选人。两次都是静默失效。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 改名可能破坏已有数据 | 改名在同一事务内**级联**到所有引用处 |
| 删除会孤立数据 | 仍被引用时**必须指定迁移目标**，否则拒绝删除；也可改用停用 |

## ADR-010 面试官必须显式选择，不做「智能推荐默认值」

**状态**：已采纳 ｜ **影响**：面试安排

### 背景

安排面试时，面试官是必填项。产品上有个看似体贴的做法：
默认选一个「最合适」的面试官，减少操作。

### 决定

**必须显式选择**，不设默认值。但下拉框按「同业务线 → 不限业务线 → 其它业务线」
分组排序，并显示每人的待面试场次。

### 理由

这个缺陷真实发生过，而且很典型：原实现里如果没传面试官，
后端会**静默挂到第一个业务面试官名下**。结果是所有面试都堆给了同一个人，
其他面试官的日程是空的 —— 而系统一切正常，只是结果全错。

**这里的关键区别是：提供排序信息 ≠ 替用户做决定。**
排序帮用户快速找到合适的人（省时间）；默认值则让用户跳过决定（制造静默错误）。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 每次都要选一下 | 排序 + 待面试场次展示，最快路径只需一次点击 |
| 用户仍可能选错 | 支持改派，改派后原面试官立即不可见；写入决策日志 |

## ADR-011 时间冲突只提示不拦截

**状态**：已采纳 ｜ **影响**：面试安排

### 背景

同一面试官时间重叠时，系统可以拦截，也可以只提示。

### 决定

只提示，允许保存。

### 理由

**「不合法」和「不合理」是两件事。** 时间重叠在现实中常见且合理：
连排两场、临时加塞、面试官自愿压缩午休。

系统能判断的是「重叠了」，不能判断的是「这是不是有意的」。
把后者当成前者，就会逼用户绕过系统（比如把时间填成假的），
反而让数据失真。

只对**真正不合法**的情况硬拦截：时间早于昨天、超过 180 天后、缺会议链接。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 可能出现真实的排期事故 | 提示文案写明冲突的具体场次与候选人，不是泛泛的「有冲突」 |

## ADR-012 录用与否决：决策日志只追加、不可编辑

**状态**：已采纳 ｜ **影响**：全局

### 决定

所有关键动作写入决策日志，日志**只追加不修改**，并记录当时的模型版本与提示词版本。

### 理由

两个作用：

1. **可举证**。候选人对筛选结果提出异议时，平台能说明「当时依据什么、谁做的决定」。
2. **可归因**。效果波动时能定位到具体版本，而不是只知道「最近变差了」。

**可编辑的日志在争议场景下不具备证明力** —— 这一条是法务评审时明确提出的。

### 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 存储持续增长 | 日志与业务表分表；归档策略按季度 |
| 写日志增加写操作 | 与业务操作同事务提交，不单独引入失败点 |
