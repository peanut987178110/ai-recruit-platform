## 2 简历主链路状态机

**状态机是开发与测试对齐的关键，每个状态的进入条件与可执行动作必须唯一。**

```mermaid
stateDiagram-v2
    [*] --> 待解析: ATS 推送 / 手工导入
    待解析 --> 待打分: 解析成功
    待解析 --> 解析异常: 字段抽取失败 / 文件损坏
    解析异常 --> 待打分: 人工补录 / 重新上传

    待打分 --> 待安排面试: 高分档（置信度≥0.85 且 总分≥75）
    待打分 --> 待复核: 中间档（总分≥45）
    待打分 --> 待定池: 低分档（总分<45 或触发否决项）

    待安排面试 --> 待复核: HR 退回
    待复核 --> 待安排面试: 采纳
    待复核 --> 待定池: 否决

    待定池 --> 待复核: 人工捞回
    待定池 --> 已归档: 满 7 天自动归档

    已归档 --> [*]
```

### 2.1 为什么没有「已拒绝」状态

低分候选人进入**待定池**并在 7 天后**归档**。归档不等于拒绝，也不触发任何对外通知。
是否拒绝、何时告知由 HR 在 ATS 中另行操作。

这是需求分析阶段与法务确认的边界：**平台不承担不利决定的执行**。
系统里根本不存在「拒绝」这个动作，也就不存在误操作导致不可撤回后果的可能。

## 3 AI 调用与三级降级

**禁止静默降级**：任何降级都必须在界面明示，否则用户会把兜底结果当作正常结论采信。

```mermaid
flowchart TD
    START(["业务能力请求"]) --> GATE{"模型网关<br/>已配置？"}
    GATE -- 否 --> HUMAN["三级：转人工<br/>原因：未配置模型网关"]
    GATE -- 是 --> PICK["按能力分层选型<br/>小 / 中 / 大 / 视觉 / 嵌入"]

    PICK --> CALL["调用模型"]
    CALL --> OK{"请求成功？"}
    OK -- 否 --> RETRY{"重试次数<br/>< 2 次？"}
    RETRY -- 是 --> WAIT["退避等待后重试"]
    WAIT --> CALL
    RETRY -- 否 --> SWITCH{"主模型不可用<br/>且有备用模型？"}

    SWITCH -- 是 --> FB["二级：切换备用模型<br/>元信息记录实际使用的模型"]
    FB --> PARSE
    SWITCH -- 否 --> HUMAN

    OK -- 是 --> PARSE["解析输出 JSON<br/>含截断修复"]
    PARSE --> PARSED{"解析成功？"}
    PARSED -- 否 --> RETRY
    PARSED -- 是 --> SCHEMA{"结果体<br/>schema 校验通过？"}

    SCHEMA -- 否 --> HUMAN
    SCHEMA -- 是 --> EVID{"打分类能力<br/>证据体非空？"}
    EVID -- 否 --> HUMAN
    EVID -- 是 --> VERSION["元信息以代码侧为准<br/>丢弃模型自报的版本号"]
    VERSION --> DONE(["返回三段结构<br/>结果体 / 证据体 / 元信息"])

    HUMAN --> HQUEUE["状态留在原处并告警<br/>由人工接手"]
    HQUEUE --> DONE

    style HUMAN fill:#ffe0e0
    style FB fill:#fff3d0
    style DONE fill:#e0f0e0
```

### 3.1 三段结构与硬性校验

```mermaid
flowchart LR
    subgraph RESULT["AI 输出：三段结构"]
        direction TB
        R1["<b>结果体</b><br/>业务字段<br/><i>按能力 schema 强校验</i>"]
        R2["<b>证据体</b><br/>原文片段 + 起止位置<br/><i>打分类能力必须非空</i>"]
        R3["<b>元信息</b><br/>模型版本 / 提示词版本<br/>置信度 / 耗时<br/><i>以代码侧为准</i>"]
    end

    R2 --> CHECK1["证据无法在原文定位<br/>→ 判为失败"]
    R1 --> CHECK2["枚举值不在约定集合<br/>→ 判为失败"]
    R3 --> CHECK3["写入决策日志<br/>供效果归因与回归对比"]

    style CHECK1 fill:#ffe0e0
    style CHECK2 fill:#ffe0e0
    style CHECK3 fill:#e0f0e0
```

**为什么版本号必须由代码侧写死**：若采信模型自报的版本号，模型可能编造一个不存在的版本，
线上出现效果波动时就无法归因到具体版本，离线回归也就失去了对比基准。

### 4.1 「未体现」与「不符合」必须区分

```mermaid
flowchart LR
    Q["简历里<br/>提到这项能力了吗？"] -- "没提到" --> A["<b>未体现</b><br/>信息缺失<br/>→ 面试中验证"]

    B -- "不符合" --> C["<b>不符合</b><br/>能力不足<br/>→ 作为负面依据"]
```

两者混为一谈，会把**表述简略的候选人误判为能力差** —— 这是简历筛选里最常见的不公平来源。

## 5 简历复核：人机分工

```mermaid
flowchart TD
    IN(["候选人进入待复核"]) --> VIEW["复核页<br/>左 60% 原文 / 右 40% 打分"]
    VIEW --> CLICK["点击能力项"]
    CLICK --> HL["左侧原文定位并高亮证据片段<br/><i>300ms 内完成</i>"]
    HL --> JUDGE{"HR 判断"}

    JUDGE -- "采信" --> ADOPT["<b>采纳</b><br/>转待安排面试"]
    JUDGE -- "不采信" --> REJECT["<b>否决</b><br/>必须选原因"]
    JUDGE -- "拿不准" --> DOUBT["<b>标记疑问</b><br/>可指派用人经理<br/><i>状态不变</i>"]

    ADOPT --> LOG["写入决策日志<br/>含当时模型版本"]
    REJECT --> REASON["原因：能力不匹配 / 经验不足<br/>简历造假疑似 / 岗位已关闭 / 其他"]
    REASON --> POOL["转待定池"]
    DOUBT --> LOG

    POOL --> RESCUE{"7 天内有人捞回？"}
    RESCUE -- "是" --> REBACK["转待复核<br/>填写捞回原因"]
    RESCUE -- "否" --> ARCHIVE["归档<br/><b>不发送任何通知</b>"]
    REBACK --> REFLOW["回流样本池"]
    ARCHIVE --> ENDD(["终态，记录仍可检索"])

    REFLOW -. "捞回后通过面试 = 误杀线索" .-> REVIEW["每周专项复盘"]

    style DOUBT fill:#e8e8ff
    style ARCHIVE fill:#f0f0f0
    style REVIEW fill:#ffe0e0
```

### 5.1 设计要点

| 要点 | 原因 |
| --- | --- |
| 采纳与否决**不设默认选中** | 防止用户无意识批量放行 |
| 中间档**禁用批量通过** | 这部分恰是模型最没把握的样本，有意增加操作成本 |
| 采纳与否决**一键完成**，无需理由即可继续 | 用户最大阻力不是「AI 不准」，而是「AI 不准还要我背责任」 |
| 否决原因**必选**但仅用于优化 | 不用于考核 HR，否则会产生应付式选择 |
| **风险提示只陈述客观事实** | 输出「近三年任职 4 家公司」，不输出「稳定性差」 |

## 6 面试题生成：差集出题

**差集出题是本产品的核心设计，且模型会违反它** —— 因此生成后有一道强制约束。

```mermaid
flowchart TD
    IN(["结构化简历 + 能力模型"]) --> DIFF["计算差集<br/>哪些能力项未体现 / 部分命中"]
    DIFF --> GEN["LLM 分层出题"]

    GEN --> BLOCK{"命中敏感话题？<br/>婚育 / 年龄 / 宗教<br/>户籍 / 政治面貌"}
    BLOCK -- 是 --> DROP["<b>整条丢弃</b><br/>记录日志"]
    BLOCK -- 否 --> ENFORCE["<b>强制差集约束</b><br/><i>模型实测会违反，必须后置纠正</i>"]

    ENFORCE --> E1["排除条款（必须没有）<br/>→ 最多 1 道真实性核验题"]
    ENFORCE --> E2["普通缺口项<br/>→ 优先保留"]
    ENFORCE --> E3["已证明项<br/>→ 每项最多 1 道确认题"]

    E1 --> FILL["缺口题不足时<br/>用缺口项补满时间预算"]
    E2 --> FILL
    E3 --> TRIM["按时间预算取舍<br/>30 分钟方案 ≤ 32 分钟"]
    FILL --> TRIM
    TRIM --> OUT(["四层题目 + 评分锚点<br/>每题关联能力项 ID"])

    style DROP fill:#ffe0e0
    style ENFORCE fill:#fff3d0
```

### 6.1 为什么排除条款不能当普通缺口项

排除条款（如「简历真实性存疑」）是给 HR 判断**合规风险**用的，
不是让候选人当面回答「你有没有造假」。实测中模型会把它当普通缺口项猛出题，
出现过 4 道的情况 —— 这在面试现场是不合适的问法。

## 7 考核反作弊：三层设计

**只有第一层是真实防线。** 这个区分是整个设计的立足点。

```mermaid
flowchart TB
    subgraph L1["第一层：服务端强制（不可绕过）—— 真实防线"]
        direction TB
        A1["<b>答案不下发</b><br/>判卷全部在服务端完成"]
        A2["<b>开考即冻结试卷</b><br/>刷新 / 换设备恢复同一份题"]
        A3["<b>服务端计时</b><br/>限时取自方案，客户端传值被忽略"]
        A4["<b>每人随机组卷 + 选项乱序</b><br/>答案重映射回原序判分"]
        A5["<b>限次与幂等交卷</b><br/>超时不可提交"]
    end

    subgraph L2["第二层：客户端信号（可绕过）—— 仅作线索"]
        direction TB
        B1["切屏 / 页面隐藏 / 多标签页"]
        B2["粘贴 / 复制 / 右键 / 打印"]
        B3["开发者工具 / 异常缩放 / 全程未聚焦"]
        B4["同类信号封顶计数<br/>+ 答题速度启发式"]
    end

    subgraph L3["第三层：人工复核 —— 最终判断"]
        direction TB
        C1["带教人看信号明细"]
        C2["决定是否作废（作废返还机会）"]
        C3["给出终评分数（及格线取方案设置）"]
    end

    A1 --> L2
    L2 --> RISK{"风险分"}
    RISK -- "≥ 15 可疑" --> QUEUE
    RISK -- "≥ 5 关注" --> QUEUE
    RISK -- "< 5 正常" --> QUEUE["复核队列<br/>按风险分降序"]
    QUEUE --> L3

    style L1 fill:#e0f0e0
    style L2 fill:#fff3d0
    style L3 fill:#e8e8ff
```

### 7.1 为什么第二层不能自动判失败

浏览器事件**技术上不可能防住有心作弊的人**，而且会大量误伤无辜场景：

| 无辜场景 | 会触发的信号 |
| --- | --- |
| 接电话时切出去 | 切屏、页面隐藏 |
| 输入法弹窗 | 失焦 |
| 笔记本合盖 | 页面隐藏、全程未聚焦 |
| 网课页面同时开着 | 多标签页 |

若据此自动判失败，会直接违背需求分析中的洞察二 ——
**误杀的代价远高于漏放**，考核场景同理。

所以三层的关系是：**服务端让作弊拿不到答案，客户端信号把可疑的挑出来给人看，最终由带教人看证据决定。**

### 7.2 考试状态机

```mermaid
stateDiagram-v2

    待开始 --> 进行中: 新人在培训窗口内开考
    进行中 --> 进行中: 心跳上报信号 / 暂存作答

    end note
```

### 7.3 选项乱序与答案重映射

这一步是**最容易出错、一旦出错全盘皆错**的地方：题目和选项都被打乱，
若判分时不把学生的答案映射回题库原序，**每一道客观题都会判错**。

```mermaid
flowchart LR
    BANK["题库原题<br/>选项序：A B C D<br/>答案：<b>B</b>"] --> SHUF["组卷时打乱选项<br/>示例：C A D B"]
    SHUF --> SHOW["下发时重映射<br/>答案 B → 显示字母 A"]
    SHOW --> STU(["学生看到<br/>选项序：C A D B<br/>作答：<b>A</b>"])
    STU --> UNMAP["交卷时反映射<br/>显示 A → 题库原序 B"]
    UNMAP --> GRADE["按 B 判分<br/>✅ 正确"]
    STU -. "若漏掉反映射" .-> WRONG["按 A 判分<br/>❌ 全盘判错"]

    style GRADE fill:#e0f0e0
    style WRONG fill:#ffe0e0
```

### 9.1 捞回记录为什么是最有价值的回流

**捞回后通过面试的案例，就是一次「差点被误杀」的实证。**
这条链路是发现误杀模式最直接的入口，因此单独列表、每周由 HR 负责人复盘，
而不是混在总体指标里被平均掉。

## 10 权限与数据隔离

```mermaid
flowchart TD
    REQ(["请求"]) --> AUTH{"Bearer Token<br/>有效？"}
    AUTH -- 否 --> HDR{"X-User-Id 旁路<br/>已开启？"}
    HDR -- "是（仅测试环境）" --> ROLE
    HDR -- "否" --> E401["401 未认证"]
    AUTH -- 是 --> ROLE["解析角色"]

    ROLE --> PERM{"该角色在此模块<br/>有此操作权限？"}
    PERM -- 否 --> E403["403 无权操作"]
    PERM -- 是 --> SCOPE["<b>查询层数据隔离</b>"]

    SCOPE --> S1["业务面试官<br/>→ 仅被指派候选人"]
    SCOPE --> S2["招聘 HR<br/>→ 本人负责岗位"]
    SCOPE --> S3["用人经理<br/>→ 本部门"]
    SCOPE --> S4["带教人 / 新人<br/>→ 本人带教关系"]

    S1 --> MASK
    S2 --> MASK
    S3 --> MASK
    S4 --> MASK
    MASK["输出前统一脱敏"] --> M1["系统管理员<br/>→ 简历正文替换为占位文本"]
    MASK --> M2["法务审计<br/>→ 联系方式替换为「已隐藏」"]
    M1 --> OUT(["返回"])
    M2 --> OUT

    style E401 fill:#ffe0e0
    style E403 fill:#ffe0e0
    style SCOPE fill:#fff3d0
```

### 10.1 两条合规硬约束

| 约束 | 原因 |
| --- | --- |
| **面试官只能看到被指派的候选人** | 避免简历在组织内无边界流动 |
| **系统管理员不可查看简历正文** | 防止运维角色成为数据合规的缺口 |

两条均实现为**查询层过滤**，而非前端隐藏 ——
前端隐藏只能防误操作，防不住有心越权。
即便是超级管理员，「不可查看简历正文」这条限制同样生效。

## 11 登录与角色差异

```mermaid
flowchart TD
    LOGIN(["登录页"]) --> TYPE{"已有账号？"}
    TYPE -- "自助注册" --> SIGNUP["可选角色受限<br/>招聘HR / 业务面试官<br/>用人经理 / 带教人"]
    TYPE -- "已有账号" --> CRED["账号 + 密码"]

    SIGNUP --> WAIT(["等待管理员启用"])
    CRED --> VERIFY{"校验通过？"}
    VERIFY -- 否 --> FAIL["提示账号或密码错误"]
    VERIFY -- 是 --> TOKEN["签发自包含令牌<br/>HMAC 签名"]

    TOKEN --> ROUTE{"角色路由"}
    ROUTE --> R1["招聘HR / HR负责人<br/>→ 候选人工作台"]
    ROUTE --> R2["业务面试官<br/>→ 面试日程"]
    ROUTE --> R3["用人经理<br/>→ 本部门候选人"]
    ROUTE --> R4["带教人<br/>→ 培训方案"]
    ROUTE --> R5["新人<br/>→ 我的培训"]
    ROUTE --> R6["法务审计<br/>→ 只读看板"]
    ROUTE --> R7["系统管理员<br/>→ 阈值与参数"]

    style SIGNUP fill:#fff3d0
```

**为什么自助注册只开放 4 种角色**：若开放高权限角色，
任何人都能给自己开一个看全量数据的账号，权限矩阵形同虚设。
系统管理员、HR 负责人、法务审计必须由管理员创建。
